# Пайплайн разработки учебника с Codex

Дата аудита: **15 сентября 2026 года**. Проект: `Uchebnik_v2`, Expo / React Native / TypeScript.

**Статус: предложение к внедрению.** Этот документ описывает существующее состояние и рекомендуемый процесс. Примеры настроек, skills, агентов и автоматизаций ниже ещё не установлены. При подготовке документа код приложения, настройки Codex и существующие незакоммиченные изменения не менялись; тесты приложения повторно не запускались.

Рекомендуемая схема: **Terra для обычной разработки → Sol для сложных изменений → Astra для наиболее трудных задач**. Luna подходит для ограниченных вспомогательных задач. Тесты исполняются скриптами без участия модели. Каждый содержательный фикс проверяется по исходному изображению страницы, а не только по уже написанному коду.

### Предлагаемый договор в `AGENTS.md`

Ниже — содержание для будущего файла, не уже действующая конфигурация:

```text
Источник истины: изображение соответствующей страницы учебника.
Описание страницы помогает навигации, но при расхождении проверяй скан.
Отделяй исходное задание от согласованной интерактивной адаптации.

Перед изменением прочитай git status, затронутую страницу и код механики.
Для существенного изменения кратко зафиксируй критерии приёмки.
Сохраняй стабильные идентификаторы страниц/заданий и прогресс ребёнка.
Генерируемые данные меняй через генератор, затем проверяй воспроизводимость.
Проверяй ошибки, повторную попытку, сброс и граничные случаи жестов.
После исправления воспроизведи самое раннее затронутое задание.

Разрешено делегировать ограниченные независимые подзадачи.
Главный агент выбирает модель роли; обычно не более двух дочерних агентов.
Дочерние агенты не создают своих агентов. Один файл имеет одного владельца.
Проверка источника и ревью по умолчанию только читают файлы.
Маленькие изменения выполняй одним агентом.

Не изменяй посторонние файлы и не добавляй их в коммит.
Коммит и push выполняй только в пределах явного разрешения пользователя.
Не включай debug-сканы и инструменты сверки в release.
Не выдавай пройденный unit-тест за проверку браузера или телефона.
```

Правила проекта дополняют ограничения среды, а не отменяют их. Текущая сессия не разрешает произвольное делегирование без запроса пользователя или применимого правила; будущий `AGENTS.md` должен явно задавать указанное разрешение и границы.

### Минимальный проектный конфиг

Предложение для `.codex/config.toml`:

```toml
model = "gpt-5.6-terra"
model_reasoning_effort = "medium"

[agents]
enabled = true
max_concurrent_threads_per_session = 2
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "medium"

[mcp_servers.unityMCP]
enabled = false
```

Лимит `max_concurrent_threads_per_session` считает **дочерних** агентов, без основного. Фактическая доступность дополнительно ограничивается клиентом. Проектное отключение Unity MCP не должно менять настройки Unity-проектов. Эти ключи описаны в актуальной документации [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) и [конфигурации](https://learn.chatgpt.com/docs/config-file/config-advanced).

**Основную модель фиксируем именно в проектном конфиге**, чтобы новый запуск CLI в учебнике автоматически выбирал Terra / medium без личного профиля. В актуальном порядке приоритетов проектный конфиг выше выбранного профиля; CLI-параметр `-m` выше обоих. Поэтому локальный маршрутизатор сможет выбирать другую модель для отдельной работы без записи в глобальные настройки. Конфиг доверенного проекта загружается отдельно от настроек пользователя. [Приоритеты настроек](https://learn.chatgpt.com/docs/config-file/config-basic).

### Автоматический выбор модели только для учебника

Разделяем три механизма:

| Механизм | Что выбирается автоматически | Граница возможностей |
| --- | --- | --- |
| Проектный `model` | Модель по умолчанию при новом запуске CLI в доверенном учебнике | Не определяет сложность запроса и не переопределяет явный `-m` |
| Проектные роли subagents | Модель назначенной роли при создании дочернего агента | Меняется модель исполнителя; основной агент остаётся на своей модели |
| Будущий `scripts/ai-task.*` | Модель отдельного запуска по типу задачи и правилам повышения сложности | Это код маршрутизатора, который ещё нужно реализовать; TOML сам не выполняет такую логику |

Основной путь для Desktop: координатор делегирует ограниченную работу подходящей проектной роли без ручного выбора модели пользователем. Логи/изложение — Luna; обычная реализация — Terra; сложные жесты и ревью — Sol; трудная архитектура — Astra. Разрешение выбирать эти роли закрепляется только в проектном `AGENTS.md`. Механизм настройки моделей дочерних агентов описан в [документации subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

**Не обещаем автоматическую смену основной модели уже открытой Desktop-задачи.** Сохранённый выбор модели и параметры клиента могут переопределить default из файла. При внедрении нужно проверить фактическую модель новой задачи; настройка дочерних ролей не меняет родителя. Для гарантированно выбранной модели отдельного запуска используем CLI с явным `-m`. Если нужен именно автоматический переход основной задачи между моделями внутри Desktop, это отдельная интеграция с поддерживаемыми средствами клиента, пока не подтверждённая и не реализованная здесь.

После создания проектного конфига обычный CLI-запуск не требует профиля:

```sh
codex -C /Users/denisislamov/WorkProjects/PET/Uchebnik_v2 --strict-config
```

Разовое явное переопределение, например для сложной архитектуры:

```sh
codex -C /Users/denisislamov/WorkProjects/PET/Uchebnik_v2 -m gpt-5.6-sol -c 'model_reasoning_effort="high"'
```

В интерактивном CLI остаются `/model` и `/status`; в Desktop доступен выбор модели в интерфейсе задачи. Доступность моделей зависит от клиента, авторизации и плана. [Выбор модели](https://learn.chatgpt.com/docs/models).

### Риски переноса настроек в другой проект

| Риск | Как ограничиваем |
| --- | --- |
| Изменение глобального model, MCP, skills или hooks затронет Unity и другие проекты | Не записывать настройки учебника в пользовательские файлы; не отключать глобальные плагины ради этого проекта |
| Личный профиль с названием учебника запускается в другом каталоге | Не использовать глобальный профиль как механизм изоляции; его имя не привязывает его к репозиторию |
| Файлы настроек размещены в общей родительской папке | Размещать их в корне `Uchebnik_v2`, не в `PET`, `WorkProjects` или домашнем каталоге |
| Другой проект открыт в прежней задаче через смену каталога | Для другого проекта использовать отдельную задачу/запуск; не полагаться на смену cwd как на сброс истории и параметров |
| Явный выбор модели в CLI/Desktop перекрывает проектный default | Показывать фактические модель и reasoning при запуске; не считать ожидаемые настройки уже применёнными |
| Проект не доверенный, поэтому его `.codex`-слой не загружен | Проверять загрузку проектной конфигурации до работы; не расширять доверие автоматически |
| Маршрутизатор случайно запущен из другого репозитория | Проверять принадлежность checkout учебнику до запуска ИИ; при несовпадении завершаться без действий |
| Недоступная модель или неограниченные повышения увеличивают расход | Без бесшумной замены; объяснять причину, ограничить повышение и число попыток |

Изоляция здесь относится к проектной конфигурации. Пользовательские/системные инструкции, установленные глобальные инструменты, история задачи и лимиты аккаунта не становятся отдельными. Порядок загрузки и требование доверия описаны в [конфигурации Codex](https://learn.chatgpt.com/docs/config-file/config-basic).

**Приёмка изоляции при внедрении:** открыть новую задачу/CLI в учебнике, затем отдельную в другом существующем проекте, затем снова в учебнике. Зафиксировать реальные модели, MCP и доступность проектных ролей во всех трёх запусках. В учебнике ожидается его политика, в другом проекте — его прежняя конфигурация без ролей/ограничений учебника. Проверить, что пользовательские настройки не изменились. Проверку Desktop и CLI провести отдельно; пока она не выполнена, автоматический выбор в Desktop не считать подтверждённым.

Не ослаблять sandbox ради удобства. Для отдельного анализа из CLI использовать `--sandbox read-only`, для реализации — `--sandbox workspace-write` при соответствующем разрешении среды. Не смешивать устаревающий набор sandbox-настроек с новой схемой permission profiles в одном примере конфигурации. [Настройка разрешений](https://learn.chatgpt.com/docs/config-file/config-basic).

## 3. Skills для этого проекта

Нужен небольшой набор предметных skills. Они должны направлять агента к исходникам и исполняемым проверкам, не дублируя десятки страниц документации в каждом контексте.

| Предлагаемый skill | Когда использовать | Обязательный результат |
| --- | --- | --- |
| `textbook-source-audit` | Правка текста, рисунка, ответа или трактовки задания | PDF-номер страницы, ID блока, факты со скана, расхождения, критерии приёмки |
| `textbook-interaction` | Рисование, drag-and-drop, выбор объектов, счёт | Инварианты механики, положительные и отрицательные сценарии, проверка мобильного интерфейса |
| `textbook-content-build` | Добавление/изменение данных курса | Изменён источник генерации, сохранены ID, генерация воспроизводима |
| `textbook-regression` | Завершение исправления или пакета изменений | Выбранные проверки, реальные команды/результаты, снимки, ограничения покрытия |
| `textbook-release` | Явно запрошены коммит, push или подготовка релиза | Проверенный diff, точный набор файлов, результаты проверок, соблюдение разрешения на публикацию |

Расположение: `.agents/skills/<name>/SKILL.md`. Для поддерживаемых skills можно задать `policy.allow_implicit_invocation: false` в `agents/openai.yaml`; это подходит release skill, который должен вызываться явно. Skill сам по себе **не переключает модель** и не выдаёт разрешение на push. [Создание skills](https://learn.chatgpt.com/docs/build-skills).

Минимальная заготовка `textbook-source-audit/SKILL.md`:

```markdown
---
name: textbook-source-audit
description: Проверка задания арифметического учебника по исходному скану перед изменением текста, ответа или взаимодействия.
---

1. Определи PDF-номер страницы, печатный номер и ID задания; не смешивай их.
2. Открой textbook/pages/page_NNN.png и соответствующий page_docs/*.md.
3. Прочитай условия и вводные подсказки, осмотри рисунок и образец письма.
4. Запиши, что ребёнок должен сделать, сколько объектов нужно и что считается ответом.
5. Раздели факты источника, согласованную адаптацию и неопределённости.
6. Сопоставь с исходными данными/генератором и UI. Не редактируй generated-файл вручную.
7. Верни короткий контракт задания и сценарии проверки. Не меняй код в режиме аудита.
```

Для `textbook-interaction` отдельно закрепить:

- Прямое действие ребёнка: предмет переносится, нужный объект выбирается на картинке; взрослое подтверждение не заменяет решение.
- Линии, диагонали и фигуры соответствуют геометрии клеток и образцу. Рамка, поля и масштабирование не сдвигают траектории.
- Для замкнутых фигур допустима произвольная начальная точка; допустимые направления движения задаются смыслом конкретного задания.
- Количество рисуемых/переносимых объектов следует условию. Нельзя превращать задание «нарисуй три» в несвязанные задания «нарисуй один».
- Области попадания удобны ребёнку, но расширение соседних областей имеет определённое правило разрешения пересечений.
- Подсказка объясняет жест; проверяются неверный жест, отпускание вне цели, повтор, сброс, смена страницы и сохранённый прогресс.

Из уже доступных общих навыков полезны `openai-docs` для настроек Codex, PDF для исходников, systematic-debugging для воспроизводимого дефекта, verification-before-completion и независимое code review. TDD применять к поведению и регрессиям, а не писать тест, повторяющий новую реализацию.

Сейчас установлен большой набор Superpowers с собственными правилами применения. Перед внедрением предметного процесса стоит согласовать активный набор: обязательные длинные обсуждения и подтверждения на каждую мелкую правку увеличивают стоимость. Не редактировать файлы в кэше установленных плагинов и не считать, что новый `AGENTS.md` отменяет обязательные инструкции среды. Предпочтительны поддерживаемые настройки skills/плагинов и короткие проектные процедуры.

## 4. Как должна работать система subagents

### Основной принцип

Главный агент владеет задачей, критериями приёмки и итоговой интеграцией. Дочерний агент получает ограниченную работу, а не копию всей истории проекта. По умолчанию — один исполнитель; второй агент появляется, когда независимое ревью или аудит действительно окупают дополнительный контекст.

| Роль | Типичная модель | Доступ и границы |
| --- | --- | --- |
| Координатор | Terra / medium; Sol для сложного пакета | План, распределение файлов, интеграция, итоговые проверки |
| Проверяющий источник | Terra / medium; Sol при сложной визуальной трактовке | Чтение 1–3 конкретных сканов, описаний и данных; без правок |
| Исполнитель | Terra / medium | Только назначенная механика и её тесты |
| Независимый reviewer | Sol / medium для жестов и общей логики; Terra для простого diff | Чтение diff, источника и тестов; без параллельного исправления тех же файлов |
| Разборщик логов | Luna / low | Ограниченный лог, группировка причин, ссылки на ошибки; без заявления о прохождении тестов |

**Маленькая правка:** один агент читает источник, исправляет, проверяет.

**Средняя правка:** сначала контракт по скану, затем реализация; после неё reviewer проверяет результат. Главный агент в это время может готовить ручной сценарий или собирать проверочные артефакты.

**Большой пакет:** параллельно можно анализировать разные страницы или независимые компоненты. Нельзя одновременно менять общий генератор, типы или одни и те же файлы тестов. Не распараллеливать реализацию до согласования общего контракта.

### Формат поручения

```text
Цель: проверить механику рисования ствола дерева.
Источник: конкретный PDF-номер, путь к PNG, page_docs и ID блока.
Разрешённые файлы: перечисление путей; остальные только читать.
Контракт: допустимы движения вверх и вниз; линия привязана к клетке.
Проверки: оба направления, короткий штрих, уход в соседнюю клетку, повтор.
Выход: вывод, file:line для проблем, выполненные команды и результаты.
Ограничения: не создавать агентов, не коммитить, не запускать общий browser runner.
```

Для первого поручения перечисляются реальные пути и ID. Общая формулировка «проверь, всё ли хорошо» не обеспечивает независимую проверку.

### Пример именованного агента

Предлагаемый файл `.codex/agents/source-auditor.toml`:

```toml
name = "source-auditor"
description = "Проверяет соответствие интерактивного задания исходному скану учебника."
model = "gpt-5.6-terra"
model_reasoning_effort = "medium"
sandbox_mode = "read-only"
developer_instructions = """
Работай только с назначенными страницами и заданиями.
Сравни исходный скан, описание страницы и текущую интерпретацию.
Отделяй факты от предположений. При неясном скане сообщи неопределённость.
Верни критерии приёмки и расхождения со ссылками на файлы.
Не редактируй файлы, не создавай других агентов и не публикуй изменения.
"""
```

Это актуальный формат отдельного файла агента с `name`, `description` и `developer_instructions`; старые примеры с `[agents.role]` и `config_file` сюда не переносим. Пара модели и reasoning задаётся вместе. Реальные разрешения нужно проверять в запущенной среде: унаследованные runtime-переопределения могут иметь приоритет над файловой конфигурацией. [Конфигурация subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

В инструментах текущей Desktop-сессии полное наследование истории сохраняет модель родителя и не допускает отдельный model override. Для более дешёвого агента нужен ограниченный или пустой fork с самостоятельным поручением. Это особенность доступного здесь инструмента, а не универсальный параметр CLI-конфига.

### Ограничение параллелизма и конфликтов

- Обычно максимум два дочерних агента. Три допустимы только для действительно независимой работы и укладываются в текущие четыре слота с родителем.
- Один владелец на `types.ts`, общие компоненты, генераторы и сгенерированный курс. Аудиторы страниц возвращают замечания; интегратор меняет генератор и регенерирует один раз.
- Один браузерный прогон на checkout: текущий runner использует общий `dist`, порт 8094 и артефакты в `docs`. Одного изменения порта недостаточно для устранения гонок за файлами.
- Для независимых реализаций использовать отдельные worktree, когда рабочие изменения можно корректно перенести. Не считать, что новая worktree автоматически содержит незакоммиченные правки исходного каталога.
- После двух неудачных гипотез пересмотреть причину и контекст; при необходимости повысить модель. Не оплачивать бесконечные одинаковые попытки.

## 5. Модели: качество, цена и назначение

### Рекомендуемая маршрутизация

Это рабочая гипотеза для нашего проекта, которую нужно проверить на реальных задачах. OpenAI описывает Astra как наиболее сильную модель для трудных задач, Sol — для сложной работы, Terra — для повседневной, Luna — для ограниченных повторяемых задач. Это не гарантия качества конкретного изменения. [Описание моделей](https://learn.chatgpt.com/docs/models).

| Работа | Начальный выбор | Когда повышать уровень |
| --- | --- | --- |
| Запуск тестов, сборка, генерация данных | **Без модели:** npm / Python / CI | При падении подключить анализ |
| Краткий разбор лога, форматирование отчёта | Luna / low | Причина не локализуется или зависит от нескольких подсистем |
| Простой тест по ясному контракту | Terra / medium | Сложные жесты, допуски, сохранение состояния |
| Проектирование регрессии и проверка тестового оракула | Terra / medium или Sol / high | Неясна трактовка источника или баг проходит существующие проверки |
| Небольшая правка компонента / контента | Terra / medium | Затрагивает несколько механик или общий генератор |
| Drag-and-drop, геометрия, tracing, восстановление состояния | Sol / medium, затем high | Повторные неудачи, сложные межкомпонентные зависимости |
| Архитектура новой механики | Sol / high | Системный редизайн, миграции данных, много противоречивых ограничений |
| Наиболее трудная архитектура / диагностика | Astra / high | Max/ultra — только после явной оценки пользы и расхода |
| Переписывание документа по утверждённым фактам | Luna / low | Нужны новые технические решения, а не изложение |

Дешёвой модели нельзя поручать единолично решать, что изображено на неоднозначном скане, и затем считать её собственные тесты доказательством. Ревью должно заново сверять критерии с источником.

На этом хосте доступны имена `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`. В отдельных инструментах есть Spark; его не включаем в базовый процесс без отдельной проверки доступности и качества. Наличие имени в документации не гарантирует его доступность во всех клиентах аккаунта.

### Что экономит больше, чем механическая смена модели

1. Передавать конкретный скан, ID и несколько файлов вместо всего учебника и полной истории.
2. Сначала локализовать дефект; не читать весь `fullBookData.ts`, когда нужна одна страница.
3. Не запускать несколько агентов для однострочного изменения.
4. Отдавать генерацию, поиск и тесты детерминированным инструментам.
5. Начинать с достаточного reasoning; high/max/ultra не назначать всем ролям.
6. Возвращать короткий отчёт и пути к артефактам вместо длинных логов в контексте.
7. Измерять стоимость **принятого исправления**, включая переделки и ревью.

Для пилота взять 5–10 задач: допуски на ягодах, направление ствола, начало замкнутой фигуры, перенос палочек, геометрия клетки, текст страницы 11. Сравнивать время до принятия, токены/кредиты, число попыток, пропущенные дефекты и повторное открытие бага. Не обещать процент экономии до такого сравнения.

## 6. Автоматизация в Codex

### Уровень A — существующие проверки без ИИ

```sh
npm run test:content
npm run typecheck
npm test
npm run test:release-guard
npm run export:web
npm run test:browser
```

Все перечисленные шаги уже объединены в `npm run test:all`. Для изменения только документации их повторный запуск не нужен. Для пакета правок механик перед итоговой приёмкой нужен полный прогон; для промежуточной итерации достаточно релевантного теста.

Пример текущей точечной регрессии:

```sh
node --experimental-strip-types --test tests/manual-feedback.test.ts
npm run export:web
node scripts/run-browser-tests.cjs scripts/manual-feedback-smoke.cjs
```

Проверка debug-режима выполняется отдельно. В одном терминале:

```sh
npm run web:debug -- --port 8082 --offline --clear
```

В другом:

```sh
npm run test:debug
```

`test:debug` ожидает отдельный debug-сервер. Обычный browser runner поднимает свой сервер; не подменять его случайно уже открытой страницей другого порта. Детали: [AUTOMATED_TESTING.md](AUTOMATED_TESTING.md).

### Уровень B — воспроизводимый запуск ИИ из консоли

CLI поддерживает `codex exec`, выбор модели, вывод JSONL через `--json`, итог по JSON Schema через `--output-schema` и запись ответа через `-o`. Это основа будущего сценария запуска, но **автоматического оптимизатора модели здесь пока нет**. [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

Пример ограниченного анализа существующего отчёта, без правок проекта:

```sh
codex exec -C /Users/denisislamov/WorkProjects/PET/Uchebnik_v2 \
  -m gpt-5.6-luna -c 'model_reasoning_effort="low"' \
  --sandbox read-only \
  -o /private/tmp/uchebnik-validation-summary.md \
  'Прочитай docs/VALIDATION.md. Кратко перечисли дату, уровни проверок и непроверенные области. Не запускай тесты, не меняй файлы и не выдавай старые результаты за текущие.'
```

Предлагаемый будущий wrapper `scripts/ai-task.*` должен принимать тип задачи, страницы/ID и список разрешённых файлов. Явная таблица маршрутизации выбирает модель; скрипт записывает модель, reasoning, ревизию, состояние рабочего дерева, команды проверок и итог. Сначала поддержать три маршрута: `audit`, `fix`, `review`. Запускать его только из локальной команды этого проекта, без глобального alias или изменения shell-профиля.

До запуска ИИ wrapper проверяет канонический корень checkout и принадлежность учебнику по явно настроенной идентичности репозитория, с поддержкой его разрешённых worktree. Одного имени каталога недостаточно. Затем передаёт `-C`, `-m` и reasoning конкретному процессу, не переписывая TOML между запусками. Повышение модели создаёт отдельный ограниченный запуск с краткой передачей контекста; это не бесшовная смена уже работающего процесса. Разрешить не более двух повышений: Terra → Sol → Astra, с причиной в отчёте и без расширения прав на файлы/публикацию.

Выбор по ключевым словам не должен незаметно давать агенту право менять файлы или публиковать их. Автоматическое повышение модели ограничить числом попыток и объяснять в отчёте. Жёсткий денежный лимит потребует отдельного механизма учёта; такого проектного ограничения сейчас нет.

### Уровень C — hooks для коротких проверок

Предлагаемая логика, **пока без установленного hook**:

| Событие | Полезное действие | Чего избегать |
| --- | --- | --- |
| `SessionStart` | Показать ветку, незакоммиченные изменения, подсказку по командам | Сборка приложения при каждом открытии |
| `PostToolUse` | Отметить изменение релевантных файлов для будущей проверки | Полный тестовый прогон после каждого изменения |
| `SubagentStop` | Проверить наличие отчёта и соблюдение назначенных файлов | Воспринимать текст «готово» как доказательство |
| `Stop` | Сверить наличие результатов для текущего состояния файлов | Бесконечный цикл: тест меняет артефакт → снова запускается тест |

Конкретный hook нужно реализовывать по актуальному контракту события и exit-кодов; эта таблица не является исполняемой конфигурацией. Пользовательские hooks требуют отдельного доверия к точному содержимому; в CLI это проверяется через `/hooks`. Несколько matching hooks могут запускаться одновременно, поэтому общий browser runner нельзя без блокировки вызывать из нескольких обработчиков. [Hooks](https://learn.chatgpt.com/docs/hooks).

Для валидности отчёта недостаточно одного commit SHA: незакоммиченный код тоже меняется. Будущий механизм должен учитывать хэш затронутых исходников, новых файлов и конфигурации. Результаты и screenshots исключаются из триггера повторного запуска. Пока такого механизма нет, состояние проверки контролирует интегратор.

### Уровень D — CI и расписания

Существующий CI оставить главным автоматическим шлюзом проверок. Следующие возможные улучшения:

1. Обязательный статус CI перед слиянием — отдельно настроить правила репозитория GitHub; сам YAML этого не гарантирует.
2. AI-review запускать на готовом diff по запросу или выбранной метке. Отчёт с замечаниями, без автоматического merge/push.
3. Ночной прогон имеет смысл при регулярных изменениях или проверке внешних зависимостей. Если изменений нет, повторный AI-анализ не нужен.
4. Для будущей работы по расписанию выбрать: продолжение текущей задачи для наблюдения или самостоятельный запуск в изолированной worktree для отдельной проверки.

Локальные задания Codex по расписанию требуют работающего приложения, доступного компьютера и проекта. Облачная задача не получает локальные сканы автоматически. Расписание не заменяет CI и не гарантирует запуск при выключенном ноутбуке. Создавать его через интерфейс/инструменты Codex после выбора нужного поведения; в рамках этого документа расписания не создавались. [Scheduled tasks](https://learn.chatgpt.com/docs/automations).

## 7. Порядок работы над конкретным заданием

| Шаг | Действие | Критерий перехода |
| --- | --- | --- |
| 1. Контекст | Статус git, PDF-номер, ID блока, затронутая механика | Понятны границы изменения и чужие незавершённые правки |
| 2. Источник | Скан + описание + вводный текст + рисунки | Записан ожидаемый результат без домыслов |
| 3. Регрессия | Воспроизвести дефект и выбрать независимый проверочный пример | Есть наблюдаемое отличие текущего поведения от контракта |
| 4. Исправление | Изменить источник данных/механику, сохранить ID | Минимальный связный diff |
| 5. Проверка | Целевой тест, браузерный жест, исходная страница рядом | Пройден позитивный и отрицательный сценарий |
| 6. Ревью | Независимо сверить скан и изменения для существенных правок | Нет неподтверждённых трактовок и критичных замечаний |
| 7. Регрессия пакета | `test:all`, при debug-изменениях также `test:debug` | Свежие результаты для итогового кода |
| 8. Приёмка | Отчёт и ручная проверка на телефоне для touch-механик | Уровни проверки и оставшиеся ограничения явно указаны |
| 9. Git | Коммит/публикация при наличии разрешения | Включены только согласованные файлы |

Для контента учитывать разные маршруты: ранние страницы описаны в `src/content/book.ts`, `childInteractions.ts` и `tracing.ts`; остальной курс собирается через `scripts/content/early_pages.py`, `overrides.py`, `build_course.py` и `src/content/fullBook.ts`. `src/content/fullBookData.ts` — генерируемый результат. Исправление только этого файла потеряется при следующей сборке.

Образец поручения координатору:

```text
Исправь задание [ID] на PDF-странице [номер].
Сначала сравни скан, описание страницы и текущую механику.
Критерии: [наблюдаемое действие ребёнка и допустимые ответы].
Сохрани идентификаторы и прогресс. Добавь регрессию на найденный дефект.
Если работа требует независимого аудита, делегируй только чтение указанной страницы.
После исправления проверь самый ранний затронутый шаг и соседние механики.
Верни изменения, реальные результаты проверок и то, что нужно проверить на телефоне.
Коммит и push в эту задачу не входят.
```

## 8. Как внедрить без лишней сложности

**Этап 1 — договор и изоляция.** Создать `AGENTS.md`, проектный `.codex/config.toml` с Terra / medium, четыре предметных skill и явно вызываемый release skill. Глобальные настройки не менять. Проверить переход учебник → другой проект → учебник отдельно в CLI и Desktop. Успех: подтверждены фактические настройки и отсутствие влияния на другой проект; Codex называет источник, сохраняет чужие изменения и выполняет подходящие проверки.

**Этап 2 — ограниченные агенты.** Добавить `source-auditor` и `reviewer`, затем при необходимости `implementer`. Провести 5–10 задач и измерить переделки/расход. Успех: параллельные агенты не конфликтуют за файлы, ревью находит реальные ошибки, стоимость принятой правки оправданна.

**Этап 3 — консольный сценарий.** Добавить wrapper для `audit/fix/review`, машиночитаемый итог и учёт проверок. Успех: по отчёту можно восстановить, какая модель что проверила и на каком состоянии кода.

**Этап 4 — hooks и расписание по необходимости.** Ввести лёгкие обработчики и только полезные повторяющиеся проверки. Успех: нет повторных прогонов без изменения исходников, конфликтов browser runner и самостоятельных публикаций.

Сейчас из перечисленного создан **только этот документ**. Рекомендуемый первый шаг внедрения — этап 1; сложная оркестрация до измерения пользы не нужна.
